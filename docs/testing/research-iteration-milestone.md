# Research iteration milestone: one understandable, measurable loop

Status: consolidated implementation branch; acceptance still open. This document is
an engineering handoff, not a claim that the UI journey or scientific result passed.

## One delivery branch

`codex/research-integration` is the sole delivery branch above `dev`, reviewed in
PR166. It contains Project authorship and observed execution, scoped MCP research
clients, annotation inspection, explicit evaluation views, variable prediction row
counts, and bounded sparse reads. Earlier component branches/PRs preserve review
history; they are not separate integration dependencies. No main promotion or release.

Benchmark inputs, target selection, evaluator access and scientific decisions belong
in the private Project/operator protocol, not product code. No benchmark-specific
screen, route, runner or database is added.

## The user's journey

1. **Open the Project.** Main explains its question, creator/start time, contributors,
   observed current work, latest result and retained failures. A Study is an effort;
   a researcher is an actor. Connected does not mean running. Opening Main starts no
   compute. The folder button opens the existing Project-folder inspector.
2. **Understand the material.** Inputs contains the assignment, controls, training
   material and selected dependencies. Opening an item creates its retained tab:
   verified dimensions/type, exact matching inspection, source, Study use and available
   actions. Technical hashes remain secondary. Older revisions never borrow newer facts.
3. **Start or continue the effort.** Open Study in its own tab. Review the question,
   criteria and exact inputs. A connected researcher receives the Project/Study locator
   and uses the supported scoped client. A person can inspect and invoke the same catalog
   capabilities/workflows through existing surfaces. No new launch-adapter product is
   required. An unavailable in-app provider is shown honestly.
4. **Follow the work.** Compact progress opens the retained effort tab. Main and Activity
   show the original workflow/attempt, actor and observed state; failures remain visible.
   Closing a tab or disconnecting an agent does not duplicate or restart admitted work.
   No decorative progress, fabricated presence or success inferred from admission.
5. **Ask with context.** The Study conversation retains the question and exact evidence
   references. An external-agent question is visibly queued until that agent picks it
   up; the copyable handoff remains available. Connection alone must never imply automatic
   dispatch. Refresh preserves the draft. Only actual edits trigger an unsaved-change warning.
6. **Inspect the outcome.** Open the retained diagnostic/report, follow evidence back to
   exact inputs, and download the prediction/method/manifest bundle. Reports and reviewed
   findings remain distinct. The summary explains what ran, what was learned and what to
   do next in plain language, with measurements and limitations available underneath.
7. **Return later.** Close and reopen the Project. The same question, input revisions,
   operations, failures, contributors and outputs remain accessible. A fresh authorized
   researcher can continue from them without a pasted recap.

## Finite finish line

- One bounded prediction effort produces retained output through supported services.
- One fresh researcher/reviewer recovers the work from the Project and publishes a
  useful evidence-linked interpretation. Do not claim another provider identity merely
  by changing a label; a multi-family swarm is not required for this small milestone.
- The actual UI journey above works at a normal desktop size and one narrow layout,
  including a failed operation, queued question, download and reopen.
- One concise report distinguishes structural validity, measured scientific quality,
  source tests, actual computation, model use and browser evidence. A poor scientific
  score is reportable; invalid output or fabricated evidence is not a pass.
- Required integrated checks pass before merging to dev. Existing workspace-capture CI
  and model-load performance failures remain open until diagnosed and qualified.

## Work order and cost discipline

1. Consolidate and reuse reviewed changes and existing evidence. No new architecture.
2. Repair the known execution/integration failures with focused tests. Freeze one
   candidate before the required combined gate; do not run broad suites on every edit.
3. Run the bounded task once, then one independently read-only review. Reuse the existing
   training inspection. A follow-up experiment is optional and must be justified by
   development evidence and fit the operator's preset allowance.
4. Perform one complete browser rehearsal and fix only blockers on that journey.
5. Record the exact branch/preview revision, outputs, scores and remaining limitations.

No recursive agents, broad hyperparameter search, foundation-model training, new paid
cloud services, 1,000-agent scaling, new harness providers, complete portability roadmap,
full-size benchmark submission, or cosmetic redesign campaign in this milestone.

External agent calls have a fixed operator allowance and hard wall-clock termination.
Tool/runtime and input readiness are checked before a model starts. After a timeout or
admission failure, inspect the original operation; do not spend another model session
retrying identical work. The scoped client itself is not a lifetime budget enforcer:
qualify the operator's allowance/termination mechanism before launching the pilot.
